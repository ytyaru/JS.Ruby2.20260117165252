# JamlにおけるUnicodeの取り扱いに関する設計思想と仕様

## 1. はじめに

この文書は、Jaml (Japanese Markup Language) が、その基礎となる文字セットであるUnicode、特にUTF-8エンコーディングをどのように取り扱うか、その設計思想、直面した課題、そして下された意思決定について記録するものである。

Jamlの目標は、人間が読み書きしやすい、日本語を中心としたマークアップ言語を提供することである。しかし、その基盤となるUnicodeは、全世界の言語を包含する巨大で複雑な体系であり、歴史的な経緯から、多くの「技術的負債」を抱えている。

この文書の目的は、JamlがUnicodeの利便性を享受しつつも、その複雑性や潜在的なリスクとどのように向き合い、ユーザーにとって安全で、開発者にとって現実的な仕様を策定したかを明確にすることにある。

## 2. 直面した課題: Unicodeの複雑性と技術的負債

Unicodeを扱う上で、我々は主に3つの大きな課題に直面した。

### 2.1. セキュリティリスク

Unicodeテキストは、特定の文脈（C言語ベースのシステム、Webサーバーなど）で解釈される際に、深刻なセキュリティ脆弱性の原因となりうる文字やシーケンスを含む。

-   **ヌルバイト (`U+0000`)**: C言語等で文字列終端と解釈されるため、ファイルシステムの不正アクセスや認証回避といった「ヌルバイト攻撃」を引き起こす。
-   **不正なバイトシーケンス (Overlong Encodings)**: UTF-8の符号化ルールを意図的に破ることで、`/` のような危険な文字を検知するセキュリティフィルターを回避する攻撃手法が存在する。
-   **正規化の問題 (Homograph Attacks)**: 見た目が酷似しているがコードポイントが異なる文字（例: ラテン文字の `A` とキリル文字の `А`）を利用し、URLを偽装するフィッシング攻撃など。

### 2.2. ローカライズの困難性 (CJK問題)

Jamlは日本語を中心としているが、Unicodeでは日本・中国・韓国の漢字が「CJK統合漢字」として同じブロックに混在している。

-   **日本語の漢字の完全な分離は困難**: `[一-龠]` のような単純な正規表現では、人名・地名で使われる異体字（例: `髙`, `﨑`）を網羅できない。
-   **トレードオフ**: `\p{Script=Han}` のように範囲を広げれば日本語の漢字を網羅できるが、同時に大量の中国語特有の漢字や、場合によってはハングルまで許容してしまい、「日本語中心」という思想と乖離する。

### 2.3. 不可視文字と曖昧な「空白」の定義

Unicodeには、表示されない、あるいは幅を持たない「不可視文字」が多数存在する。これらは、特定の言語では必須の制御文字であるが、他の文脈では意図しないバグの原因となる。

-   **文脈依存の「空白」**: 「空白文字」の定義は、Unicodeの一般カテゴリ (`Zs`, `Zl`, `Zp`)、ECMAScriptの `\s`、同 `trim()` メソッドで、それぞれ範囲が異なる。
-   **分類の困難**: `Cc` (Control), `Cf` (Format) といった制御文字や、`Lo` (Letter, Other) に分類されるが見た目は空白の文字など、その扱いを単純に決めることができない文字が多数存在する。

## 3. Jamlの設計判断と仕様

上記の課題は、Jamlパーサー単体で完璧に対処するにはあまりにも巨大で、コストに見合わない。完璧な安全性を追求すればパフォーマンスが犠牲になり、パフォーマンスを追求すれば安全性が脅かされる。

したがって、Jamlは**「防御的プログラミング」**の思想に基づき、以下の**現実的な妥協案**を採用する。

### 3.1. セキュリティ: 費用対効果の高い対策に集中する

-   **ヌルバイト (`U+0000`) は、Jamlフォーマットの仕様として明確に禁止する。**
    -   **理由**: 危険性が極めて高く、かつテキストに含まれる正当な理由が皆無であり、単純なチェックで検出可能であるため。これは、Jamlがエコシステム全体に対して負うべき最低限の倫理的責務である。
    -   **実装**: 上位の `Jaml.parse()` APIや、専用の `TextSanitizer` が、パーサーの入り口でこの文字を検出し、エラーをスローする責務を負う。
-   **不正なバイトシーケンスやホモグラフ攻撃への対処は、Jamlパーサーの責務範囲外とする。**
    -   **理由**: これらの攻撃への対処は、文脈に強く依存し、極めて高度な専門知識と膨大な計算コストを要する。これをパーサーに内蔵するのは非現実的であり、OS、ブラウザ、または専用のセキュリティライブラリが担うべき責務である。

### 3.2. ローカライズ: 網羅性を優先し、副作用を許容する

-   **パイプ省略形の親文字として許容される漢字は、`\p{Script=Han}` プロパティを持つ文字とする（将来的な方針）。**
    -   **理由**: 日本語で使われる漢字（特に人名・地名の異体字）を漏れなくサポートすることの利益は、中国語特有の漢字を誤って許容してしまうデメリットを上回ると判断する。
    -   **注**: 初回実装 (`RbEmFast`) では、互換性と単純性のために `[一-龠...]` を採用するが、これは将来的に拡張されるべき課題として認識する。

### 3.3. 不可視文字: Jamlの文脈で「意味のある」分類を行う

-   **Unicodeの公式分類 (`Cc`, `Cf`等) は、あくまで基礎的な定義として参照する。**
-   **Jamlパーサーが実際に利用するのは、Jamlの構文解析の文脈で再定義された、より実用的な文字グループとする。**
    -   **例**: `jaml/protocol/jaml/invisible.js`
        -   **目的**: RbEmなどのインライン要素が「不可視文字のみ」で構成されることを防ぐ。
        -   **定義**: Unicodeカテゴリが `Letter` や `Symbol` であっても、人間が視認できない文字（例: ハングルフィラー、点字の空白）は、このグループに含める。
-   **`Cs` (Surrogate), `Co` (Private Use), `Cn` (Unassigned) は、Jamlパーサーの責務範囲外とする。**
    -   **理由**: これらの文字の妥当性を検証するコストは、得られるメリットに見合わない。Jamlは、「入力テキストは、整形式のUnicode文字列である」ことを前提とする。

### 3.4. 責務範囲外とするUnicodeカテゴリ

Jamlパーサーは、以下のUnicode一般カテゴリに属する文字の妥当性検証を、その責務範囲外とする。

-   **`Cs` (Surrogate)**: Jamlは、入力テキストが「整形式のUnicode文字列」であることを前提とする。分断されたサロゲートペアのような、破損したデータの検証は行わない。
-   **`Co` (Private Use)**: 私用領域の文字の意味や妥当性は、それを利用するアプリケーションとフォントの責任範囲であり、Jamlは関知しない。将来的に、`jaml/protocol/unicode/` 層で、ユーザーが有効な私用領域を指定するためのAPIを提供する構想は存在するが、Jamlコアパーサーの責務ではない。
-   **`Cn` (Unassigned)**: 未割り当てコードポイントの存在チェックは、膨大なコストを要する。これは、より高度な `TextSanitizer` のようなバリデーション層が担うべき責務であり、Jamlパーサーの責務ではない。

## 4. 結論

Jamlは、Unicodeという強力だが危険も伴う基盤の上に成り立っている。我々は、すべての問題を解決できるという傲慢さを捨て、Jamlの責務範囲を明確に定義し、その範囲内で最大限の安全性と実用性を追求する。

Jamlのユーザーと開発者は、この文書に記された設計判断と、その背景にあるトレードオフを理解した上で、このフォーマットを利用することが推奨される。
