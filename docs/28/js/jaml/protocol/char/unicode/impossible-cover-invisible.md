# なぜ「すべての不可視文字」を完璧に網羅することは不可能なのか

## 1. 問題提起

Jamlパーサーは、構文の妥当性を検証する上で、「不可視文字のみ」で構成される要素（親文字、ルビ文字など）を無効として扱いたい。これを実現するには、「不可視文字」とは何かを明確に定義し、その全リストを網羅する必要がある。

しかし、この「すべての不可視文字を網羅する」というタスクは、一見単純に見えて、**原理的に不可能**である。この文書は、その理由を技術的な観点から解き明かし、Jamlが採用する現実的なアプローチの論理的根拠を示すものである。

## 2. 「不可視性」の定義の困難さ

困難の根源は、Unicode規格において**「この文字は不可視である」という単一の、明確なプロパティが存在しない**ことにある。文字の「可視性」は、単一の属性ではなく、複数の要因が絡み合った結果として決定される。

### 2.1. 要因1: Unicodeの一般カテゴリ (General Category)

Unicodeは、すべての文字を `Lu` (大文字), `Po` (句読点), `Zs` (スペース区切り) などの一般カテゴリに分類している。このうち、以下のカテゴリは「不可視」の強力な候補となる。

-   `Cc` (Other, Control): ASCII由来の制御文字。定義上、グリフを持たない。
-   `Cf` (Other, Format): テキストの表示形式を制御する文字。定義上、グリフを持たない。
-   `Zl` (Separator, Line): 行区切り文字。
-   `Zp` (Separator, Paragraph): 段落区切り文字。
-   `Zs` (Separator, Space): 幅を持つ空白文字。

**限界**: この分類だけでは不十分である。例えば、`U+2800` (BRAILLE PATTERN BLANK) は、カテゴリ上は `So` (記号) に分類されるが、そのグリフは空白である。一般カテゴリは、文字の「機能」や「由来」に基づいており、必ずしも「見た目」と一致しない。

### 2.2. 要因2: Unicodeの派生プロパティ

Unicodeは、一般カテゴリを組み合わせて、より具体的な性質を示す「派生プロパティ」を定義している。

-   **`White_Space`**: 空白として扱われるべき文字のリスト。`Zs` カテゴリの文字に加え、`U+0009` (タブ) などを含む。
-   **`Default_Ignorable_Code_Point`**: テキスト処理において、デフォルトで無視されるべき文字のリスト。`Cf` カテゴリの多くや、`U+2060` (ワードジョイナー) などが含まれる。

**限界**: これらも「不可視性」を定義する上で非常に有用だが、完全ではない。例えば、`U+200D` (ゼロ幅ジョイナー) は `Default_Ignorable_Code_Point` であるが、絵文字の合字を形成するなど、表示に**積極的に関与**する。これを単純に「無視できる」あるいは「不可視」と断定することはできない。

### 2.3. 要因3: フォントの実装依存

文字が最終的にどのように表示されるか（グリフを持つか、空白になるか、豆腐 `□` になるか）は、**フォントファイルの実装に完全に依存する。**

-   ある文字が、フォントAにはグリフが実装されているが、フォントBには実装されていない、という状況は日常的に発生する。
-   `U+1D159` (MUSICAL SYMBOL NULL NOTEHEAD) のような特殊な記号は、音楽記号用のフォントでなければ、空白として表示される可能性が高い。
-   Unicodeは、あくまで「このコードポイントはこの文字を意味する」という対応関係を定義するだけであり、その**具体的な字形（グリフ）を規定しているわけではない。**

**結論**: 「グリフを持たない文字」をプログラムで100%正確に特定することは、特定のフォントを指定しない限り、不可能である。

### 2.4. 要因4: 文脈依存の不可視性

一部の文字は、単独では意味をなさず、前後の文字との関係性の中で初めてその「不可視の」役割を果たす。

-   **ハングルフィラー (`U+115F`など)**: これらはUnicode上は `Lo` (文字) に分類される。単独で存在すると空白に見えるが、ハングルの字母と組み合わせることで、正しい文字組版を実現するために存在する。
-   **合字制御 (`U+200C`, `U+200D`)**: これらも `Cf` (フォーマット) であり、単独では不可視だが、アラビア文字や絵文字の表示を根本から変える力を持つ。

これらの文字を、単純に「不可視だから無効」と判断することは、特定の言語のテキストを破壊することに繋がりかねない。

## 3. Jamlの戦略: 「完璧な網羅」から「実用的な定義」へ

以上の分析から、「すべての不可視文字を完璧に網羅する」という目標は、技術的に達成不可能であることが明らかになった。

したがって、Jamlはアプローチを転換する。目標を「完璧な網羅」から、**「Jamlの構文解析において、問題を引き起こす可能性のある文字を、客観的な基準に基づいて定義し、それに対処する」**ことに再設定する。

### 3.1. 「Jaml Invisible Chars」の定義

Jamlは、「不可視文字」を以下の**いずれか**の条件を満たす文字として、**仕様として定義する**。

1.  **`General_Category` が `Cc`, `Cf`, `Zl`, `Zp`, `Zs` のいずれかである。**
2.  **`Default_Ignorable_Code_Point` プロパティが `true` である。**
3.  **`White_Space` プロパティが `true` である。**

### 3.2. この戦略の正当性

-   **客観性**: この定義は、すべてUnicodeの公式プロパティに基づいている。なぜある文字が含まれ、別の文字が含まれないのかを、常に論理的に説明できる。
-   **自動化可能性**: この定義に合致する文字のリストは、`UnicodeData.txt` と `PropList.txt` からプログラムによって100%自動生成が可能である。
-   **責務の明確化**: この定義から外れる文字（例: `U+2800` BRAILLE PATTERN BLANK）の扱いは、Jamlの「不可視文字」の責務範囲外であると明確に宣言する。これにより、パーサーが責任を負うべき範囲が限定され、仕様が安定する。

このアプローチは、Unicodeの無限の複雑性に対して、我々がコントロール可能な、堅牢で保守性の高い防壁を築くための、唯一の現実的な戦略である。
