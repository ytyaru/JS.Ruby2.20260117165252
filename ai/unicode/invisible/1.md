この「不可視文字」以外にも、将来は別の分類で文字をグループ化したいため、以下のような汎用コードを書きました。

```js
export class CharGroup {
    #items = []; // 文字の配列 (重複なし)
    #string = ''; // itemsを結合した文字列
    #regexp = null; // キャッシュされた正規表現
    #label = {};   // ラベル

    /**
     * @param {string|Array} source - 文字列、文字配列、またはコードポイントの範囲/単体を含む配列
     * @param {object} [label={}] - グループのラベル { ja: '日本語名', en: 'EnglishName' }
     */
    constructor(source, label = {}) {
        this.#label = label;
        let codePoints = [];

        if (typeof source === 'string') {
            codePoints = [...source].map(c => c.codePointAt(0));
        } else if (Array.isArray(source)) {
            for (const item of source) {
                if (typeof item === 'number') {
                    codePoints.push(item);
                } else if (Array.isArray(item) && item.length === 2) {
                    for (let i = item[0]; i <= item[1]; i++) {
                        codePoints.push(i);
                    }
                } else if (typeof item === 'string') {
                    codePoints.push(...[...item].map(c => c.codePointAt(0)));
                }
            }
        }

        // 重複を除外して items と string を生成
        this.#items = [...new Set(codePoints)].map(cp => String.fromCodePoint(cp));
        this.#string = this.#items.join('');
    }

    get label() { return this.#label; }
    get string() { return this.#string; }
    get items() { return [...this.#items]; } // 不変性を保つためにコピーを返す

    get regexp() {
        if (this.#regexp === null) {
            // 正規表現の特殊文字をエスケープする
            const pattern = this.items.map(char => 
                '\\^$.*+?()[]{}|'.includes(char) ? `\\${char}` : char
            ).join('');
            this.#regexp = new RegExp(`[${pattern}]`, 'gu');
        }
        return this.#regexp;
    }

    is(text) {
        if (typeof text !== 'string' || text.length === 0) return false;
        return [...text].every(char => this.#string.includes(char));
    }

    has(text) {
        if (typeof text !== 'string') return false;
        this.regexp.lastIndex = 0; // グローバル正規表現の状態をリセット
        return this.regexp.test(text);
    }

    remove(text) {
        if (typeof text !== 'string') return '';
        this.regexp.lastIndex = 0;
        return text.replace(this.regexp, '');
    }
}
```

しかし、「他の環境」や「今後の拡張」を考慮した際のリスクと、現在のコードの問題点を整理します。
1. なぜ「例外」は起きなかったのか
JavaScriptの正規表現エンジン（V8やJavaScriptCore）には上限がありますが、それは非常に巨大です。

    文字クラス内の文字数: 2300文字程度は全く問題ありません。数万文字レベルで初めて警告や制限が議論される世界です。
    ソースコードの長さ: regexp.source が 5KB 程度であれば、ブラウザのパース制限（数MB単位）には遠く及びません。

2. 真の懸念点は「例外」よりも「不具合」
現在の CharGroup 実装には、環境によって不可視文字を正しく判定できない（または壊れる）致命的な欠陥が1つあります。
【サロゲートペア問題】
items を生成する際、String.fromCodePoint(cp) を使っていますが、正規表現を構築する際に join('') しているため、サロゲートペア（U+10000以上の文字、今回のMn等に含まれる可能性があります）が「2つの独立した不正な文字」として文字クラス [] の中に入ってしまいます。

    期待: [𝌆] (1文字として判定)
    現実: [\uD834\uDF06] (不正なサロゲート単体での判定になり、マッチしない)

3. 「コードポイント範囲判定」への移行を推奨する理由
将来的に他の文字グループ（数万文字に及ぶ漢字など）を扱う場合、以下の理由で「範囲判定（二分探索）」の方が圧倒的に安全で堅牢です。

    メモリ効率: this.#string や巨大な正規表現文字列を持たず、[start, end] の数値配列（Range）だけで管理できる。
    確実性: サロゲートペア問題を完全に無視できる（数値として比較するため）。
    ポータビリティ: 正規表現の長さ制限を気にする必要が一切なくなる。

もし「どのような環境でも安定して動かしたい」のであれば、以下のような ranges を保持する形への変更を検討されてはいかがでしょうか。
js

// constructor内で範囲(ranges)を正規化して保持
// [ [0, 32], [127, 160], ... ]

is(text) {
    return [...text].every(char => {
        const cp = char.codePointAt(0);
        // rangesを二分探索して cp が含まれるか判定
        return this.#isInRange(cp); 
    });
}

## 2. 人力抽出リスト（heuristic.tsv）の作成方法

自動抽出では網羅できない、あるいは「実態として不可視」として扱われる文字を、外部の情報源と目視確認（PDFチャート）を組み合わせて定義します。

### 2.1. ブログ記事からの初期抽出

まず、以下の2つの技術記事から、不可視文字として紹介されているコードポイントを抽出します。

- **1.txt**: [https://tech-blog.s-yoshiki.com](https://tech-blog.s-yoshiki.com)
- **2.txt**: [https://gigazine.net](https://gigazine.net)

これらをマージした中間リスト（`3.tsv`相当）を作成する。

### 2.2. Unicode公式チャートによる目視検証

上記で抽出した文字について、[Unicode公式のCode Charts](https://www.unicode.org)（PDF）を確認し、実態が「不可視」であるかを一文字ずつ判定します。

- **判断の根拠**:
  - **不可視判定**: PDF内で「点線の四角枠」で囲まれており、図形（グリフ）が描かれていないもの。これらはそのままリストに維持、または新規追加する。
  - **可視判定**: PDF内で「実線の黒い図形」が描かれているもの。これらは専用フォントがあれば表示されるべき文字であるため、リストから除外する。

#### 検証結果の反映
- **除外 (3-1.tsv)**:
  - `0x2800` (BRAILLE BLANK): PDF上で微小な8つの点（図形）が確認されたため、本来は可視文字として扱う。
- **追加 (3+1.tsv)**:
  - ブログ記事に漏れていたが、PDFで点線枠であることを確認した以下の文字を補完。
    - `0x2011`, `0x2028`〜`0x202E`, `0x2066`〜`0x2069`, `0x180B`〜`0x180D`, `0x180F`

### 2.3. 最終的な heuristic.tsv の生成

ブログ抽出分から「可視判定分」を削除し、「漏れ補完分」を追加したものを `4.tsv` とし、これを **`src/db/heuristic.tsv`** として確定させます。

### 2.4. 抽出・加工用Pythonコード例

```python
import requests
import re

def extract_from_web():
    urls = [
        "https://tech-blog.s-yoshiki.com",
        "https://gigazine.net"
    ]
    all_codes = set()
    headers = {'User-Agent': 'Mozilla/5.0'}
    
    for url in urls:
        res = requests.get(url, headers=headers)
        res.encoding = res.apparent_encoding
        # U+XXXX 形式の抽出
        found = re.findall(r'[uU]\+([0-9a-fA-F]{4,6})', res.text)
        all_codes.update({int(c, 16) for c in found})
    
    # PDF検証に基づいた補正
    to_remove = {0x2800}
    to_add = {0x2011, 0x2028, 0x2029, 0x202A, 0x202B, 0x202C, 0x202D, 0x202E, 
              0x2066, 0x2067, 0x2068, 0x2069, 0x180B, 0x180C, 0x180D, 0x180F}
    
    final_heuristic = (all_codes - to_remove) | to_add
    
    with open("src/db/heuristic.tsv", "w", encoding="utf-8") as f:
        for code in sorted(list(final_heuristic)):
            f.write(f"0x{code:04X}\n")

if __name__ == "__main__":
    extract_from_web()

コードは注意してご使用ください。
